# ADR-0002: сессия внутри Telegram Web

- Статус: принято для технического исправления F01
- Дата: 30.09.2026
- Основание: пользователь сообщил об отказе подтверждения сессии в Telegram Web; это не согласование пилота или P-01…P-06.

## Контекст и причина

Telegram Web открывает Mini App в iframe другого сайта. Политика `SameSite=Lax` из § 4 плана мешает передаче сессии в таком контексте. Локальный браузерный сценарий с реальным HTTPS, синтетическими API и рабочим UI воспроизводит экран «Не удалось подтвердить сессию» после успешного POST входа. Vercel Logs API отказал в доступе, но CLI показал две последовательности `GET /me → 401`, `POST /auth/telegram → 200`, `GET /me/permissions → 401` в Production 30.09.2026 в 10:03:45–10:03:50 МСК. Это согласуется с дефектом cookie; точное совпадение отдельного запроса со скриншотом не установлено.

## Решение

Единая политика cookie `impuls_session` для входа и выхода: `HttpOnly; Secure; SameSite=None; Path=/; Partitioned`, без `Domain`. Срок новой сессии остаётся 12 часов; выход отзывает серверную сессию и удаляет cookie в текущем разделе хранения. Идентификатор по-прежнему случаен, в БД хранится только SHA-256. Токен не передаётся в JSON, URL или браузерные хранилища.

`Partitioned` изолирует cookie по сайту верхнего уровня. Это механизм CHIPS, описанный в [MDN](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/Third-party_cookies/Partitioned_cookies). API Next.js установленной версии поддерживает `partitioned` (локальная документация `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md`).

## Последствия

F01 сможет читать cookie внутри Telegram Web. При смене верхнего сайта (например, переходе между Telegram Web и отдельным окном приложения) требуется отдельный вход; cookie одной секции хранения не открывает другую. Старые клиенты без CHIPS могут игнорировать `Partitioned`; при полном запрете сторонних cookie они всё ещё могут показывать отказ сессии. Android/iOS и Safari требуют ручной проверки.

`SameSite=None` допускает межсайтовую отправку cookie, поэтому проверки точного `Origin` и session-bound CSRF остаются обязательными для всех мутаций. Вход проверяет `Origin`, Telegram HMAC и allowlist; выход и операции задач проверяют `Origin` и CSRF. GET не выполняет бизнес-мутации. Полномочия и отзыв проверяются сервером на каждом запросе. Runtime, API, БД и P-решения не меняются.

## Миграция и откат

Миграция БД не нужна. После выпуска повторный вход заменяет старую cookie новой; до подтверждения сессии рабочие данные не показываются. Выход удаляет cookie с теми же атрибутами. Откат политики на `Lax` возвращает дефект в iframe; ранее созданные серверные сессии истекают или отзываются обычным способом.

## Проверки

Сценарии и точные результаты записываются в `docs/verification/2026-09-30-telegram-web-session.md`: воспроизведение Lax, положительный вход, reload, HttpOnly, изоляция верхних сайтов, отдельное окно, выход, формат, lint, TypeScript, unit и сборка. Синтетический браузерный сервер не подменяет интеграционные проверки PostgreSQL или ручную приёмку Telegram.
