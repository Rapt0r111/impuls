# ADR-0034: ежедневная копия Production через GitHub Actions

- Статус: предложено; включается владельцем (секреты репозитория)
- Дата: 10.10.2026
- Авторы и утверждающие: исполнитель задачи; основание — решение владельца P-06 от 10.10.2026 («копия раз в сутки, RPO 24 ч, RTO 1 день, ответственный — владелец»)

## Контекст и причина

P-06 требует ежедневную копию и проверенное восстановление (§ 8, § 12 плана). Production — бесплатный проект Supabase (`enicnfevahcuiqvwmhgp`, PostgreSQL 17.6). По документации Supabase ([Database Backups](https://supabase.com/docs/guides/platform/backups)) ежедневные копии доступны только на тарифах Pro и выше; бесплатным проектам рекомендуется самим выгружать данные и хранить копию вне платформы. Локальная репетиция `bun run test:restore` (05.10.2026) доказывает, что архив `pg_dump` восстанавливается, но не создаёт копий Production.

## Решение

- Workflow `.github/workflows/backup.yml`: по расписанию раз в сутки (00:30 UTC, 03:30 МСК) и вручную.
- `pg_dump --format=custom --schema=impuls --schema=impuls_meta` клиентом PostgreSQL 17. Только схемы приложения: служебные схемы Supabase (`auth`, `storage` и др.) приложение не использует и в чужой кластер не восстанавливаются.
- Подключение — строка Supavisor в режиме session (порт 5432): по документации Supabase прямое подключение бесплатного проекта идёт по IPv6, а GitHub Actions поддерживает только IPv4.
- Каждая копия до сохранения восстанавливается в пустой PostgreSQL 17.6 (service container) скриптом `scripts/verify-backup.mjs`: недостающие роли создаются как NOLOGIN, `pg_restore --single-transaction --exit-on-error --no-owner` с сохранением ACL, затем проверки: история миграций — префикс миграций репозитория; балансы совпадают с журналом начислений (критерий остановки P-06); счётчики строк по таблицам без самих данных.
- Копия шифруется `age` на открытый ключ владельца (секрет `BACKUP_AGE_RECIPIENT`); закрытый ключ в GitHub не попадает. Незашифрованный файл удаляется на runner.
- Зашифрованная копия и отчёт проверки сохраняются артефактом прогона, срок хранения 14 дней. Копия, не прошедшая проверку, всё равно сохраняется, а прогон завершается ошибкой.

## Последствия

- GitHub хранит только шифротекст и счётчики строк. Ключ расшифровки — у владельца; потеря ключа делает копии бесполезными.
- Секрет `BACKUP_DATABASE_URL` даёт доступ к Production; на старте это пароль роли `postgres`. Отдельная роль только для чтения — открытый пункт.
- Срок хранения 14 дней выбран исполнителем (у Supabase Pro — 7). Он короче срока удаления P-02 (90 дней), поэтому стёртые данные исчезают из копий не позже чем через 14 дней после удаления. Срок хранения утверждает владелец (§ 8).
- Ежедневное подключение, вероятно, снимает и приостановку бесплатного проекта при простое; это вывод, не проверено.
- Восстановление в Supabase-проект, роли входа и пароли в копию не входят (роли кластерные); после восстановления пароли `impuls_app`/worker задаются заново.

## Миграция и откат

Схема БД не меняется. Включение: владелец задаёт два секрета и запускает workflow вручную. Откат: удалить или отключить workflow; копии остаются до истечения срока артефактов.

## Проверки

- `tests/integration/backup-verify.test.ts` (PostgreSQL 17.6): согласованная копия принимается, временная БД удаляется; отставание Production от репозитория допустимо, расхождение — ошибка; рассогласование баланса с журналом — ошибка; нечитаемый архив — исключение.
- `tests/verify-backup.test.ts`: извлечение ролей из GRANT/REVOKE/DEFAULT PRIVILEGES/POLICY.
- Ручная репетиция команд workflow (`docs/verification/2026-10-10-daily-backup.md`).
- Не проверено: прогон на GitHub, подключение к Supabase через Supavisor, восстановление в отдельный Supabase-проект.
