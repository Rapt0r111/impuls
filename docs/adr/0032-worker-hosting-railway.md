# ADR-0032: размещение worker в контейнере на Railway

- Статус: предложено (выбор площадки, регион и бюджет требуют подтверждения владельца, P-02/P-06)
- Дата: 10.10.2026
- Авторы и утверждающие: исполнитель задачи; утверждает владелец

## Контекст и причина

ADR-0001 оставил worker F08 вне Vercel Functions: процессу нужен постоянный цикл `--watch`/`--expire-watch`, а не HTTP-запрос. ADR-0020 и [runbook](../operations/synthetic-workers.md) описали два отдельных процесса, отдельные роли БД (`impuls_worker`, `impuls_expiry_worker`), ограниченный restart и остановку SIGTERM → drain → внутренний deadline 20 с → внешний hard stop через 25 с. Площадку они не выбирали; systemd-шаблоны в `ops/systemd/` требуют своего Linux-сервера, которого у проекта нет. На 10.10.2026 worker не размещён (`docs/verification/2026-10-08-production-app-release.md`), поэтому в Production не работают уведомления и автоистечение резервов — блокер пилота R1 (чек-лист § 4).

Требования к площадке для пилота до 10 участников (P-06): постоянный процесс Node.js 24, исходящие TLS-соединения к Supabase и `api.telegram.org`, секреты вне репозитория, перезапуск при сбое с лимитом, настраиваемое время между SIGTERM и SIGKILL, журнал stdout, регион в ЕС рядом с Supabase `eu-north-1`. Входящий HTTP не нужен.

## Решение

1. **Образ.** `apps/worker/Dockerfile` (контекст — корень репозитория, `.dockerignore` в корне): Bun 1.4.2 ставит зависимости по `bun.lock` и собирает тот же `dist/index.mjs`, что `bun run build:worker`; финальный слой — `node:24.21.0-bookworm-slim` с бандлом и одним внешним пакетом `pg` (и его зависимостями), процесс под пользователем `node`. Node запускается напрямую как PID 1, чтобы SIGTERM доходил до обработчика `installWorkerShutdown`. Runtime и пакетный менеджер не меняются.
2. **Площадка (предложение).** Railway: два сервиса из одного репозитория и одного образа, без входящих портов. Конфигурация как код: `ops/railway/notifications.json` (`--watch`) и `ops/railway/expiry.json` (`--expire-watch`); путь к файлу задаётся в настройках каждого сервиса. В них: `restartPolicyType=ON_FAILURE`, `restartPolicyMaxRetries=5`, `drainingSeconds=25` (по умолчанию у Railway 0, то есть SIGKILL сразу), `overlapSeconds=0`, одна реплика в `europe-west4-drams3a` (Нидерланды), `watchPatterns` только для файлов worker. Выход 0 при выключенном флаге не перезапускается.
3. **Почему Railway.** Не нужен свой сервер (обновления ОС, SSH, systemd), сборка из GitHub при push в `main`, отдельные переменные окружения на сервис, параметры restart и draining задаются в репозитории. Отвергнуто: Vercel Cron и функции (нет постоянного процесса, ADR-0001); GitHub Actions по расписанию (неточный cron, расход минут, нет непрерывного цикла); Supabase Edge Functions/pg_cron (переписывание worker и прав, отдельный ADR); собственный VPS с systemd — рабочая альтернатива, тот же образ или шаблоны `ops/systemd/` подходят, но требует администрирования.
4. **Подключение к БД.** Supabase session pooler (`aws-0-eu-north-1.pooler.supabase.com:5432`, логин `impuls_worker.<project-ref>` / `impuls_expiry_worker.<project-ref>`): он доступен по IPv4 и держит постоянное соединение. TLS — по `SUPABASE_CA_CERT_B64`, без `ssl*` параметров в URL (их отклоняет `assertWorkerTlsUrl`). Роли остаются отдельными; приложение worker URL не получает.
5. **Вход ролей.** Роли созданы `NOLOGIN` (000021, 000027). Пароль не может быть в миграции, поэтому владелец один раз выполняет в SQL Editor Supabase `ALTER ROLE … WITH LOGIN PASSWORD …` для каждой роли (runbook, раздел Railway). Прочие атрибуты (`NOINHERIT`, `NOBYPASSRLS`, отсутствие членства) не меняются.

## Последствия

- F08 и автоистечение F06 получают площадку; включение доставки, напоминаний и истечения остаётся отдельными флагами в окружении каждого сервиса.
- Новый обработчик данных: через Railway проходят Telegram ID получателей и токен бота. Это входит в открытый вопрос P-02 о регионах и условиях платформ.
- Стоимость: у Railway платный тариф; точная цена в этой работе не проверялась (railway.com недоступен из среды исполнителя) — часть бюджета P-06.
- Railway `restartPolicyMaxRetries` ограничивает число перезапусков без окна 300 с из systemd-шаблона; после исчерпания оператор перезапускает вручную.
- При новом деплое старый процесс получает SIGTERM после запуска нового; `overlapSeconds=0` минимизирует окно, когда работают два процесса. Захват уведомлений (`SKIP LOCKED`, lease) и истечение (блокировки quota → balance → заявка) рассчитаны на конкурентные процессы.

## Миграция и откат

Миграций БД нет. Включение: шаги владельца в runbook. Откат: удалить сервисы Railway или снять флаги и перезапустить (процесс выйдет с `disabled`), затем `ALTER ROLE … NOLOGIN`. Переход на VPS — тот же образ (`docker run … --watch`) или `ops/systemd/`.

## Проверки

`docs/verification/2026-10-10-worker-container.md`: сборка образа, состав `node_modules`, запуск обоих режимов на PostgreSQL 17.6 под ролями с LOGIN, SIGTERM через `docker stop`, отказ при неверной роли, без TLS-сертификата и при выключенном флаге. Не проверено: сборка и запуск на Railway, соединение через Supabase pooler под ролями worker, поведение Railway при остановке (draining), реальный Bot API.
