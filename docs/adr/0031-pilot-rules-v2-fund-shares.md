# ADR-0031: версия правил пилота — корректировка и бонус как доли фонда

Статус: принято локально, 10.10.2026. Основание: решение владельца P-04 от 10.10.2026, вариант Б ([реестр](../implementation/2026-10-09-owner-decisions.md#решения-от-10102026)); `IMPLEMENTATION_PLAN.md` § 5 (версии правил не переписываются, бонус — не более одного из вариантов версии), § 7 (экран «Проверка»), § 10; ADR-0030.

## Контекст

Владелец решил: проверяющий может снизить базу до 50 % фонда задачи и выбрать один бонус +10 % или +25 % фонда. ADR-0030 задаёт варианты только абсолютными числами (`maxXp`, бонус `xp/points`), одинаковыми для всех задач версии. Решение владельца выражено долями фонда, а фонды задач разные, поэтому абсолютная форма его не передаёт. Административного маршрута для публикации версий правил нет.

## Решение

- **Вторая форма вариантов в версии правил** (`definition.acceptance`):
  - `adjustment: { minPercent }` — целое 0…100. Для задачи с фондом F база допустима от `ceil(F × minPercent / 100)` до F (повышать выше фонда нельзя). Округление вверх не даёт опуститься ниже названной доли.
  - бонус `{ code, title, percent }` — целое 1…100; начисление `floor(F × percent / 100)` отдельно по XP и баллам. Округление вниз не даёт превысить названную долю. Бонус, который на малом фонде округляется до 0 XP и 0 баллов, для этой задачи не показывается; остальные бонусы остаются.
  - Смешение форм в одном объекте (`minPercent` вместе с `maxXp/maxPoints`, `percent` вместе с `xp/points`) или неверное значение отключает соответствующую возможность, как и в ADR-0030: значений по умолчанию нет. Абсолютная форма ADR-0030 продолжает работать без изменений (нижний предел 0).
- **Доли разрешаются на сервере от сохранённого фонда задачи.** `acceptanceOptions(definition, fund)` возвращает точные числа; очередь проверки и проверка выбора используют одну функцию, поэтому форма и сервер не расходятся. Фонд и версия правил задачи фиксированы после назначения, значит повтор с тем же ключом даёт тот же результат.
- **Контракт.** `acceptance.options.adjustment` получает `minXp`, `minPoints` (по умолчанию 0 для ответов, сохранённых раньше). Ниже минимума — 422 `AWARD_INVALID` с новой причиной `adjustment_below_limit`; выше — прежняя `adjustment_exceeds_limit`. Верхние пределы контракта расширены до границы столбца журнала, потому что доля большого фонда может превысить прежний предел 1 000 000.
- **Публикация — миграция `000039`.** Если есть версия `mode = synthetic` с `acceptance.enabled = true`, новая версия копирует последнюю такую версию и заменяет в `acceptance` только `adjustment` и `bonuses` (фонды, часовой пояс, уровни — решение P-04 «А»), автор — автор исходной версии. Если такой версии нет (на Production 10.10.2026 в `rule_sets` не было ни одной строки), публикуется версия только из решений владельца: `mode = synthetic`, `timeZone = Europe/Moscow`, приёмка включена с этими вариантами; автор — действующий держатель `admin.rules` (владелец после начальной выдачи). Пороги уровней не задаются: владелец их не утверждал, профиль покажет уровни как ненастроенные. Номер — `max + 1` (на пустой таблице — 1), `effective_from = clock_timestamp()`. Прошлые версии не меняются. Без исходной версии и без держателя `admin.rules` (пустая база, CI) ничего не публикуется.
- **Кому применяется.** Задача хранит версию правил, выбранную при создании; новые варианты действуют только для задач, созданных с новой версией. Форма создания задачи показывает версии по убыванию номера, поэтому новая версия идёт первой.

Почему миграция, а не админ-интерфейс версий правил: решение одно и записано владельцем; миграция воспроизводима, видна в истории и в `pgmigrations`, не требует нового права и экрана. Админ-маршрут `GET/POST /admin/rules` остаётся отдельным срезом, если версии начнут меняться часто.

## Последствия

- Баланс, рейтинг, профиль, «Первый результат», возврат начисления и защита суммы в БД (ADR-0030) не меняются: в журнал по-прежнему пишется база + бонус.
- `down` миграции намеренно запрещён: опубликованная версия может быть связана с задачами; исправление — новой версией.
- Применение к Production выполняет оператор БД (владелец) по общей процедуре миграций; эта запись его не подтверждает.

## Не решено

- Общий предел бонусов за период и отдельное право назначать бонус (P-04): сейчас — `task.review` в точной области.
- Обоснование для ненулевого бонуса отдельным полем (§ 5): сейчас используется общее обязательное основание решения.
