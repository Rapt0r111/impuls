# ADR-0006: синтетический личный профиль и «Первый результат»

Статус: инженерная базовая линия локального тестового среза, 02.10.2026; P-04/P-05 не утверждены.

F05 (§ 11 плана) требует уровни, профиль и уникальную выдачу. Используем существующие lifetime XP и версии правил, без новой экономики, зависимостей или смены транспорта.

Профиль доступен только самому активному субъекту через `GET /api/v1/me/profile`, без параметров, при `SYNTHETIC_PROFILE_ENABLED=true` (по умолчанию false). Рейтинг области и чужие профили этим правом не открываются. Ответ содержит баланс, время чтения, уровень и основание первого результата.

Настройка уровней — `definition.progression.levelThresholds` у правил `mode=synthetic`: 1–100 строго возрастающих безопасных целых чисел, первый порог 0. Выбирается последняя вступившая в силу версия с ключом progression по effective_from, затем version_number и UUID. Пустая/ошибочная новая конфигурация не возвращает старую. Без настройки уровень неизвестен, а не выдуман. Уровень — номер последнего достигнутого порога по текущему lifetime XP. Исправление XP может понизить вычисляемый уровень; смена месяца его не сбрасывает. Примеры порогов существуют только в тестах, миграция не задаёт шкалу.

Миграция 000015 сохраняет одно `first_result` на пользователя, версию условия 1 и ссылку на XP-запись принятия целой задачи R1, включая нулевой фонд. Выдача после блокировки баланса находится в той же транзакции, что review, XP/баллы, аудит, outbox и идемпотентный ответ. Победитель при конкурентных приёмках — первая успешно зафиксированная выдача; проигравшая/откаченная транзакция ничего не сохраняет. Публичного достижения или дополнительных XP/баллов нет.

Для исторических синтетических приёмок миграция выбирает минимальные created_at и UUID исходной XP-записи; provenance=migration явно отличает восстановление. Неизвестная история до журнала не реконструируется. Коррекция не переписывает источник достижения. Профиль показывает sourceCorrected и не объявляет такое достижение действующим: политика отзыва/повторной активации остаётся P-04. Последующие приёмки не перевыдают запись. R2-вехи этим условием не поддерживаются.

Таблица закрыта от PUBLIC/API-ролей; runtime имеет только SELECT/INSERT, RLS и проверку основания trigger с search_path=pg_catalog без SECURITY DEFINER. Server authorization проверяет субъект и сессию. FK ON DELETE CASCADE служит очистке синтетических фикстур владельцем БД; runtime не может удалять ни источник, ни выдачу. Откат схемы запрещён после новых выдач; откат приложения сохраняет журнал. Перед внешним выпуском требуется 000015 до кода приёмки, проверка резервной копии и PostgreSQL 17.6. Supabase/Vercel в этой задаче не изменяются.

Проверки: независимые границы порогов, неверные конфигурации; PostgreSQL replay/гонки/rollback/права/миграция; HTTP no-store/отзыв/параметры; Chromium→API→БД и состояния 320/360/390/1280 px. F05/R1 и приёмка устройств остаются открытыми.
