# ADR-0038: мгновенные сигналы об изменениях через Supabase Realtime

- Статус: принято локально; на Production не применено
- Дата: 14.10.2026
- Авторы и утверждающие: исполнитель по просьбе владельца 14.10.2026 (карточка «Какой механизм мгновенных обновлений делаем вместо частого опроса?», выбран «Supabase Realtime»).

## Контекст и причина

Открытые экраны обновлялись опросом раз в минуту. Владелец возразил против частого опроса из-за нагрузки на сервер и попросил другой механизм. Нужно, чтобы новая задача, начисление или решение по заявке появлялись у участника сразу, а нагрузка не росла с числом открытых экранов.

## Решение

- **Сигнал без данных.** Триггеры БД (миграция 000045) вызывают `realtime.send({kind}, 'change', тема, false)` после записи в `tasks`, `ledger_entries`, `account_balances`, `redemptions`, `reward_versions`. Сигнал не несёт ни названий, ни сумм: клиент получает его и перечитывает обычный API, где действуют права. Ложный или поддельный сигнал вызывает лишь лишнее перечитывание.
- **Адресаты.** Записи баланса и журнала сигналят только владельцу. Задачи, заявки и каталог сигналят всем активным участникам (в организации не больше десяти человек); экран перечитывает только открытые запросы, а доступ к данным решает сервер.
- **Тема.** `impuls-` + SHA-256 от (секрет БД ‖ id участника). Секрет лежит в `impuls.realtime_secret`, недоступной рабочей роли; функция `impuls.realtime_topic(uuid)` выдаёт тему маршруту `GET /api/v1/me/realtime`. Без секрета подписаться на чужую тему нельзя. Публичные каналы Realtime не требуют входа, поэтому защитой служит неугадываемая тема, а не токен: Realtime не знает наших сессий, а подпись JWT секретом проекта потребовала бы хранить этот секрет в Vercel.
- **Отказоустойчивость.** Без расширения Realtime (обычный PostgreSQL, тесты) функция сигнала ничего не делает; сбой отправки гасится и не отменяет бизнес-транзакцию. Сигнал уходит вместе с фиксацией транзакции, откат сигналов не оставляет.
- **Клиент.** `@supabase/realtime-js` 2.117.3 (MIT) подгружается отдельным фрагментом после показа экрана. Сигнал за 400 мс собирается в одно `invalidateQueries({refetchType:'active'})`. После повторного подключения данные обновляются сразу. Пока подписка жива, опрос раз в минуту заменяется страховочным раз в пять минут; без подписки остаётся минута, сон опроса без касаний сохраняется.
- **Включение.** Маршрут отвечает `{enabled:false}`, пока нет `REALTIME_ENABLED=true`, `REALTIME_URL` (адрес проекта Supabase, https) и `REALTIME_PUBLISHABLE_KEY` (публикуемый ключ `sb_publishable_…`, он виден в браузере) либо миграции 000045. Приложение при этом остаётся на опросе.

## Последствия

Права, контракты записи и экономика не менялись. Новая зависимость во фронтенде; публикуемый ключ и адрес проекта попадают в ответ API и в браузер (это их штатное свойство). Сообщения `realtime.send` хранятся в `realtime.messages` три дня (данных в них нет). Мгновенность зависит от доступности Supabase Realtime; бесплатный тариф ограничивает число одновременных соединений и сообщений в секунду (значения проверять по актуальной документации перед пилотом).

## Миграция и откат

Порядок выкладки: 1) миграция 000045; 2) в Realtime Settings проекта разрешить публичные каналы (в документации Supabase пункт назван «Channel Restrictions» / «Allow public access»; если разрешены только приватные, подписка не получит сигналов, а приложение останется на опросе); 3) переменные Vercel и новый деплой. Откат: убрать переменные (приложение возвращается к опросу) или `DROP TRIGGER … realtime` по пяти таблицам новой миграцией; секрет и функции безвредны. Миграция вперёд, как принято в проекте.
