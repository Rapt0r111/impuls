# ADR-0025: доставка нейтральных уведомлений через Telegram Bot API

- Статус: принято как техническое решение для synthetic-контура; включение для реальных участников ждёт P-01…P-06
- Дата: 09.10.2026
- Авторы и утверждающие: исполнитель задачи; продолжение реализации R1 по просьбе владельца в сессии 09.10.2026

## Контекст и причина

§ 8 плана и строка F08 в § 11 требуют, чтобы outbox-worker отправлял нейтральные сообщения через Bot API, а сбой отправки менял статус и число попыток, но не откатывал решение и не создавал начисление. ADR-0012 намеренно оставил в worker только симуляцию (`async () => "simulated"`) и перечислил, что обязан описать будущий адаптер: неоднозначный результат, повтор, HTTP 429/403, лимиты, согласие и реальные адреса. До этого решения в коде не было ни одного вызова `api.telegram.org`.

## Решение

- **Один транспорт, два режима.** `processNotificationSimulation(pool, claim, transport, enabled, delivery)` получает `delivery: "simulation" | "telegram"` (по умолчанию `simulation`). Режим `simulation` по-прежнему не читает Telegram ID и принимает только квитанцию `simulated`. Режим `telegram` принимает только `delivered`; несовпадение квитанции — обычный повтор.
- **Миграция 000032.** Состояние `delivered` и коды `rate_limited`, `recipient_unreachable` добавлены в очередь и неизменяемый журнал попыток. Допустимые пары фаза/код остаются закрытым списком: `retry` ← `transport_unavailable|timeout|rate_limited`; `failed` ← те же и `attempts_exhausted`; `suppressed` ← `recipient_inactive|unsupported_kind|recipient_unreachable`. Терминальные записи по-прежнему не переоткрываются. Откат миграции запрещён, как у 000021/000023.
- **Chat ID.** Worker по-прежнему не может читать `users`. Новая SECURITY DEFINER-функция `impuls.lock_notification_recipient_chat(uuid)` с `search_path=pg_catalog` и правом EXECUTE только у `impuls_worker` возвращает один `telegram_id` активного получателя (иначе NULL) и держит `FOR SHARE` до конца транзакции, как `lock_notification_recipient`: отзыв допуска ждёт завершения текущей попытки, а следующая попытка уже подавляется.
- **Адаптер** `apps/worker/src/telegram.ts`: `POST {base}/bot{token}/sendMessage` с телом `{chat_id, text}` и фиксированным нейтральным текстом из `neutralNotification`; `redirect: "error"`; таймаут 5 с через общий `AbortSignal`. Исключения, URL, описание ответа и токен наружу не выходят.
- **Классификация ответа.**
  - 200 и `ok:true` → `delivered`.
  - 429 → `rate_limited`; повтор не раньше `max(собственный backoff, retry_after)`, верхняя граница 3600 с.
  - 403 и 400 «chat not found» → `suppressed/recipient_unreachable` без повторов (бот заблокирован, пользователь не запускал бота или аккаунт удалён).
  - Прочие 4xx/5xx, сетевые ошибки, не-JSON → `transport_unavailable` с прежним backoff 30/60/120/240 с и лимитом пять попыток.
  - 401 и 404 (неверный токен или метод) → `NotificationTransportFatal`: транзакция откатывается, worker завершается с `WORKER_UNAVAILABLE`, чтобы не сжечь попытки всех событий.
- **Включение.** Второй независимый флаг `TELEGRAM_DELIVERY_ENABLED=true` поверх `SYNTHETIC_NOTIFICATIONS_ENABLED=true`; токен в `TELEGRAM_BOT_TOKEN` только в окружении worker (не в приложении, не в клиентском bundle, не в репозитории). `TELEGRAM_API_BASE_URL` допускается только как `http://` на loopback (двойник для тестов); иначе старт отклоняется. Без флага поведение прежнее: сеть не используется, токен не читается.
- **Наблюдение.** JSON-журнал worker использует `mode: "telegram"` при включённой доставке. Сводка и список в приложении показывают новые состояния и причины фиксированными подписями. Поле контракта `mode: "simulation"` не менялось, чтобы не ломать читателей; имя очереди остаётся историческим.

## Последствия

- Доставка at-least-once. Bot API не участвует в транзакции PostgreSQL: если запрос принят, а запись результата не удалась (потеря lease, обрыв), будет повтор, и получатель может получить то же нейтральное сообщение дважды. То же возможно при таймауте после фактической отправки. Начисления, баланс, квоты и событие outbox при этом не меняются, что проверено тестами. Exactly-once не заявляется.
- Сообщения не содержат названий задач, отчётов, оснований и имён (тот же `neutralNotification`); inline-кнопка WebApp не добавлена.
- Фактическая доставимость зависит от того, что получатель запускал бота; иначе результат — `recipient_unreachable`. Проверка `allows_write_to_pm` при входе не реализована.
- `outbox.mode` остаётся `synthetic`: срез не вводит режим реальных данных. Отправка на реальные аккаунты возможна только владельцу окружения, включившему оба флага. Допустимость Telegram для реальных данных — P-02, получатели и согласие — P-01.
- Классификация опирается на коды ответов, а не на тексты, кроме «chat not found» для 400. Соответствие кодов актуальной документации Bot API в этом срезе по первоисточнику не сверялось.

## Миграция и откат

Применить 000032 после 000031. Откат миграции запрещён (история попыток); отключение — снять `TELEGRAM_DELIVERY_ENABLED`, worker вернётся к симуляции. Строки со статусом `delivered` остаются в журнале, сводка в приложении продолжит их показывать.

## Проверки

- `tests/integration/telegram-delivery.test.ts` (одноразовая БД, миграции 000001–000032):
  - доставка и неизменность баланса, журнала начислений и outbox;
  - отсутствие chat ID в режиме симуляции и права ролей `impuls_worker`/`impuls_app`;
  - несовпадение квитанции, подавление неактивного получателя, сериализация с отзывом допуска;
  - `recipient_unreachable` без повторов, `retry_after` с верхней границей и нижней границей собственного backoff, пять попыток;
  - отсутствие текста исключения в сохранённых данных, fatal при 401, закрытый список кодов в БД;
  - читатели сводки и попыток показывают новые состояния без идентификаторов и текста;
  - собранный worker против локального HTTP-двойника Bot API: тело запроса, 403/429, 401, отказ запуска без токена и при нелокальном адресе, симуляция без флага.
- `apps/worker/src/telegram.test.ts`: форма запроса, таблица кодов ответа, `retry_after`, fatal, отсутствие токена в ошибке, отказ от неверных chat ID, проверка базового адреса и токена.
- Контракты: новые состояния и коды принимаются, посторонние отвергаются.
- **Не проверено:** реальный Bot API с настоящим токеном, фактическое получение на Android/iOS, лимиты Telegram под нагрузкой, пользователи, не запускавшие бота, hosting worker с токеном, P-01…P-06.
