# Проверка main без серверного CI (2026-10-21)

GitHub Actions недоступны до сброса минут (~1 ноября), поэтому шаги `.github/workflows/check.yml` прогнаны локально на PostgreSQL 17.6. Проверяли `main` (4db9094, слияние PR #26) и ветку `fix/select-list-stacking` (b3323b9, исправление перекрытия открытого списка из PR #25).

## Окружение

- PostgreSQL 17.6 (сборка `@embedded-postgres/linux-x64` из npm, та же версия, что образ `postgres:17.6` в CI), `pg_c_utf8` доступен. Кластер поднимался заново перед каждым прогоном.
- `pg_dump` и `psql` 17.7 из conda-forge, путь передан через `PG_BIN`.
- Bun 1.4.2 (как в CI), Node 22.22.0 (в CI Node 24.21.0).
- Chromium 141 из `/opt/pw-browsers`, при этом Playwright 1.62.1 ожидает другую сборку. Для запуска на пути `chromium_headless_shell-1234` созданы символические ссылки на установленный Chromium. Это настройка контейнера, в репозитории ничего не менялось.

## Причины

1. **main: audit, reward-audit, admin-catalog падают в браузере.** Playwright не может кликнуть по пункту открытого списка: элемент «не стабилен», список перекрыт контентом страницы. Причина в анимации входа (`fill-mode: both` оставляет `transform`), из-за неё `.audit-filters` становится контекстом наложения. Это тот же дефект, что описан в `2026-10-16-dropdown-select.md`. Исправление есть в `fix/select-list-stacking` (b3323b9): на этой ветке vitest-часть `test:task-slice` проходит 501/501 на чистой базе.
2. **fix: `embedded-access.mjs` падает на `Network.setCookieControls` (Invalid parameters).** Команда CDP не поддерживается Chromium 141 из контейнера. Проверка встроенного режима Telegram здесь не подтверждена.
3. **«Интеграция» падает из-за самого `scripts/local-ci.mjs`, не из-за кода.** Шаг запускает весь `tests/integration`, а `ledger-corrections.test.ts` требует `TEST_APP_ORIGIN`, который задаёт `test:task-slice` позже. В `check.yml` такого шага нет, хотя комментарий в `local-ci.mjs` говорит, что порядок совпадает с workflow. Этот шаг нужно убрать из `ci:local` или перенести после `test:task-slice`.
4. **Флейки на той же базе, не подтверждённые как дефекты.**
   - `admin-catalog.test.ts`: браузерный тест упирается в таймаут по умолчанию (5 с) на холодном старте. Проходил в двух из четырёх прогонов.
   - `rules-management.test.ts`: тест параллельных публикаций один раз получил не `ok` для одной из четырёх публикаций. Причину не установил.
   - Тесты, которые считают строки в `impuls.rule_sets`, ожидают чистую базу: на повторном прогоне той же базы `expected 41 to be greater than 41`. В CI база каждый раз новая, поэтому это не падение в CI, но `ci:local` должен сбрасывать базу.
5. **`task-management.mjs` (fix): console error «WebSocket connection to wss://realtime.example.test … Establishing a tunnel via proxy server failed».** Тест требует пустой список ошибок консоли, а приложение открывает Realtime-сокет на фиктивный хост из `verify-task-slice.mjs`. В песочнице это блокирует прокси. В CI, вероятно, будет ошибка DNS, то есть то же падение. Не подтверждено, проверить после сброса минут.

## Не проверено

- Шаги после `task-management` в `test:task-slice` (`task-history`, `task-edit-cancel`, `ledger-corrections`, `leaderboard`) не выполнялись: vitest-часть и `task-management` падали раньше. Прогонял варианты скрипта с пропуском `embedded-access` и `task-management`, но общая vitest-часть снова падала на флейках из пункта 4. Итог по этим четырём браузерным шагам нужен из серверного CI.
- Android и iOS, Telegram WebView, Realtime на двух телефонах, Production: вне этой проверки.
- Значения в таблице получены на локальной сборке PostgreSQL и Chromium, поэтому серверный CI после сброса минут должен подтвердить их.

## Что предлагаю

1. Слить `fix/select-list-stacking`: он убирает падения audit, reward-audit и admin-catalog на main.
2. Убрать из `scripts/local-ci.mjs` шаг «Интеграция» (весь `tests/integration`) или перенести его после `test:task-slice`. Сбрасывать базу перед каждым прогоном.
3. Явный таймаут для браузерных тестов в `admin-catalog.test.ts` (например, 60 с).
4. Заглушить Realtime в `task-management.mjs` или отфильтровать ошибку WebSocket к фиктивному хосту.
5. Проверить `embedded-access` и оставшиеся браузерные шаги на CI после сброса минут или на Chromium нужной версии.
