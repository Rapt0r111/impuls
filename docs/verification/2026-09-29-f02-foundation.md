## Подтверждено кодом

- `db/migrations/000004_permissions.js` создаёт области и назначения действий, ограниченные сроком и точной областью. Изменение назначения отзывает сессии затронутого пользователя. Таблицы закрыты от `PUBLIC`, для `impuls_app` включены RLS и серверные политики.

- `tests/integration/permissions.test.ts` содержит отрицательные сценарии для соседней области, иного действия, будущего/истёкшего назначения и отзыв сессии при изменении права. Для выполнения нужен PostgreSQL с миграциями.

## Не проверено и следующий шаг

- Миграция `000004` не применялась к удалённой Supabase и не проверялась локально: в этой среде нет `MIGRATION_DATABASE_URL`, `TEST_DATABASE_URL`, PostgreSQL CLI и Docker. Первый CI-прогон коммита `388f772` на PostgreSQL 17.6 успешно выполнил миграцию, `bun run check` и все 4 integration-теста. Общий job завершился ошибкой на `bun run demo:test`: на runner отсутствовал исполняемый Chromium Playwright. После установки браузера повторный [CI-прогон коммита `01c722f`](https://github.com/Rapt0r111/impuls/actions/runs/36521893472) завершился `success`: миграция, `bun run check`, 4 integration-теста и `bun run demo:test` прошли.
- F02 пока не проверяет права на объекте задачи или заявки: эти операции относятся к последующим срезам F03/F06. Управление назначениями и аудит относятся к F07. P-01 определит реальные области и ответственных, P-02 — допустимость контура и данных. До этих решений используются синтетические записи.
- Telegram WebView Android/iOS и отзыв действующего входа на устройстве не проверены.

## Supabase после применения миграций

- Проект `enicnfevahcuiqvwmhgp` (`Rapt0r111's Project`, PostgreSQL 17.6) перед изменением содержал миграции 1–3, но не `access_scopes`/`role_bindings`. В `impuls.users` была одна ранее добавленная тестовая запись; её данные не считывались. Миграции `000004` и `000005` применены через Supabase MCP как `impuls_scoped_permissions` и `impuls_permission_function_acl`; те же имена файлов записаны в `impuls_meta.pgmigrations`, чтобы `node-pg-migrate` не повторил их.
- После `000004` Supabase вернул две новые таблицы с RLS и нулём строк. SQL-проверка подтвердила `SELECT` для `impuls_app` и отсутствие `SELECT` у `anon`/`authenticated`; обе политики адресованы только `impuls_app`. Триггер `role_bindings_revoke_sessions` включён. После `000005` у trigger-функции `PUBLIC EXECUTE = false`, `impuls_app EXECUTE = true`, `SECURITY DEFINER = false`.
- Попытка `BEGIN; SET LOCAL ROLE impuls_app; SELECT ...; COMMIT;` через Supabase MCP отклонена: `permission denied to set role "impuls_app"`. Поэтому фактическое чтение этим подключением не подтверждено. CI проверил этот путь с суперпользовательским тестовым подключением; сквозной Production API-тест ниже отдельно подтвердил реальное чтение.
- Для сквозной проверки создана временная синтетическая запись пользователя и 10-минутная сессия с SHA-256 токена в БД. Production `GET /api/v1/me` и `GET /api/v1/me/permissions` с этим cookie вернули `200`, список полномочий — пустой. После удаления обеих тестовых строк повторный запрос `/me/permissions` вернул `401`. Контрольный список таблиц вновь показал 1 прежнего пользователя, 1 прежнюю сессию, 0 областей и 0 назначений. Cookie и raw токен не сохранялись в отчёте; временный локальный файл удалён. Это подтверждает реальное чтение через deployed Function и текущий `DATABASE_URL`, но не доказывает имя роли в этом URL.
- Supabase security advisors после миграций оставили прежние замечания: у закрытого журнала `impuls_meta.pgmigrations` RLS без политики; в общем `public` функция `rls_auto_enable()` с `SECURITY DEFINER` доступна `anon` и `authenticated` ([remediation](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable)). Эти объекты не менялись в срезе F02; назначение общей функции требует отдельной проверки владельца проекта.
- Первый CI-прогон ветки `codex/r1-supabase-f02` применил обе миграции, но `bun run check` упал в новом тесте: на обычном PostgreSQL 17.6 нет Supabase-ролей `anon` и `authenticated`. Тест изменён: для отсутствующей роли проверка возвращает `false`; фактическое отсутствие грантов у этих ролей подтверждено отдельным SQL-запросом в Supabase. [Повторный CI-прогон](https://github.com/Rapt0r111/impuls/actions/runs/36525222876) завершился `success`: миграции, `bun run check`, 5 PostgreSQL integration-тестов и `bun run demo:test` прошли.
