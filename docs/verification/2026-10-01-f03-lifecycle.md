## Подтверждено кодом

- `db/migrations/000012_task_lifecycle.js`: отдельное `task.view`, таблица `task_events`, уникальная пара задачи/версии, допустимые сочетания типа/статуса/ссылок, RLS и SELECT/INSERT для `impuls_app`. UPDATE/DELETE/TRUNCATE runtime запрещены. PUBLIC и имеющиеся роли Data API не получают гранты. Runtime не вставляет `snapshot`. Ссылки submission/review сохраняются как UUID, а не FK: история не переписывается при административной очистке этих записей. FK задачи с CASCADE обслуживает административную очистку синтетических фикстур; runtime не может удалять задачи. Это не политика хранения реальных данных (P-02).
- `packages/domain/src/tasks/events.ts`, `manage.ts`, `write.ts`, `reviews.ts`: события create/assign/start/submit/return/accept пишутся в той же транзакции, что задача, отчёт или решение, начисления, аудит/outbox и сохранённый ответ. Replay не пишет новое событие. Ошибка записи события откатывает операцию. Время берётся из серверного `updated_at` перехода; в приёмке совпадает со временем решения/начисления. Фонды, версия правил и ID исполнителя сохраняются на событии; отображаемые имена читаются из текущих users. Сессия начала/сдачи проверяется повторно после ожидания блокировки и перед commit.
- `task_events` старых задач содержат только снимок текущего состояния на момент миграции. Ранее не записанные начала работы и другие переходы неизвестны. Прежние submissions/reviews остаются в истории отчётов. Интерфейс сообщает эту границу явно.
- `packages/domain/src/tasks/history-access.ts`, `history.ts`, `timeline.ts`: собственное назначение в допустимом статусе либо активное `task.view` в точной области. Create/assign/review/admin не дают чужую историю автоматически. Авторизация и содержимое читаются в одном SQL statement/snapshot; скрытый и отсутствующий объект одинаково дают not_found. Нет userId из клиентского запроса. Пагинация по версии, а не времени, устойчива при одинаковых timestamp.
- `packages/contracts/src/task-timeline.ts` и GET `/api/v1/tasks/:id/timeline`: UUID, ограниченные integer cursor/limit, запрет неизвестных/повторных query-параметров, 400/401/403/404/503, request ID и private/no-store. Старый `/history` расширен тем же отдельным правом. Route Handlers не содержат SQL.
- UI: собственная лента ниже формы отчёта; обе истории в проверке и списке управления при отдельном праве области. View-only пользователь видит «Задачи и история», без формы создания/назначения. Loading, empty, pagination, 503/offline с сохранёнными данными/временем чтения, 401/403 и 404 скрывают защищённые данные. Обновление и страницы сохраняют несданный отчёт и основание решения. После мутаций соответствующий query cache инвалидируется. Заголовки, авторы/даты, фонды и текстовая подпись снимка используют существующие токены.

## Независимые сценарии и обнаруженные сбои

`tests/integration/task-lifecycle.test.ts`: 10 тестов. Ожидаемые восемь переходов v1–v8 и авторы заданы независимо; отчёты с возвратом/повторной сдачей и приёмкой дают ровно 23 XP и 11 баллов. Повторы не меняют восемь событий. Разные ключи одновременно начинают работу только один раз; одинаковые ключи получают один ответ. Коллизия версии события откатывает статус и idempotency; исправление фикстуры позволяет повторить тот же запрос. Проверены точная область, отсутствие view у create/assign/review/admin, view-only без мутаций, чужая/истёкшая/отозванная сессия и истёкшее/отозванное право. Реальное ожидание PostgreSQL task lock не разрешает replay после истечения сессии. Реальные HTTP проверяют контракты и нераскрытие данных, браузер с view-only сессией читает события и причины, затем скрывает их при отзыве допуска.

`tests/integration/task-lifecycle-migration.test.ts`: 2 теста в отдельной временной БД. SQL старых миграций исполняется перед 000012; создание уже существующей кластерной роли пропускается только в тестовом bootstrap. Старое состояние v9 получает один snapshot без выдуманного автора/старого времени. Down разрешён до новых событий и запрещён после них; события сохраняются. Временная БД удаляется после проверки.

Сбои исправлены, не скрыты: типизированный union результата API первоначально не сужался; ESLint запретил переменную `module` в новом migration test; общий predicate первоначально открывал исполнителю некорректно назначенный draft (пойман старым тестом). Сохранён запрет черновика для участника, отдельное view допускает его. Два старых Playwright-поиска любого alert находили служебный Next route announcer — поиск сужен до формы решения и раздела журнала. Новый тест терял toggle после смены доступного имени при раскрытии — locator теперь привязан к контролу, а доступные имена проверяются действиями. Первый визуальный просмотр показал перекрытый золотой цвет и тесное соседство пояснения с фокусом; исправлена специфичность и добавлен отступ 12 px, затем выполнен подтверждающий проход.

## Эксплуатация, источники и ограничения

Перед любым будущим выпуском этого кода нужны миграции 000008–000012: запись событий теперь обязательна для шести операций и при отсутствующей таблице безопасно откатывается. Для непрерывной истории нужно согласованное окно без мутаций между миграцией и переключением приложения: старый код события не пишет. Нельзя удалять миграцию при новых событиях или task.view bindings; откатывается приложение с сохранением схемы. Рост истории, retention и резервное копирование требуют политики P-02 и проверки восстановления. Реальное task.view назначается только после P-01; административного UI выдачи прав пока нет. Worker не реализован этим срезом.

Проверены [Supabase Data API security](https://supabase.com/docs/guides/api/securing-your-api) и [changelog PostgreSQL minor upgrade](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes). Changelog index и релевантная запись прочитаны как Markdown через Invoke-RestMethod (web open index вернул Unsupported content-type). В новой миграции нет ltree, legacy pgcrypto PGP, float btree_gist или custom selectivity operators. Используется установленный проектом node-pg-migrate, а не Supabase CLI; его замена нарушила бы зафиксированную архитектуру. Внешние advisors, фактическая версия/экспозиция общего Supabase-проекта и его новые миграции в этой работе не проверялись и не менялись.

Не проверены: PostgreSQL 17 CI, Telegram Android/iOS, нагрузка порога 30/60 с, восстановление БД, внешний выпуск. Требуют следующих контрактов: редактирование/отмена, компенсации F04, F05–F08. P-01…P-06 не утверждены; F02/F03/F04 и R1 целиком не завершены.
