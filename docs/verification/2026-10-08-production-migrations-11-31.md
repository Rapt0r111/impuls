# Выпуск миграций 000011–000031 в Supabase — 08.10.2026

Основание: запрос владельца «Выпускай миграции» и открытый пункт из `2026-10-08-production-telegram-login.md` (на Production было 10 из 31). Проект `enicnfevahcuiqvwmhgp`, PostgreSQL 17.6, только синтетические данные; P-01…P-06 не утверждены.

## Что сделано

- SQL `up` каждой миграции получен загрузкой JS-файла со стабом `pgm.sql` (в 000011–000031 других конструкций нет) и применён по одной транзакции через Supabase MCP `apply_migration` под именами `impuls_*`. К каждой добавлена запись `INSERT INTO impuls_meta.pgmigrations`, как в выпуске F03.
- Порядок 000011 → 000031 без пропусков. Исходные файлы в `db/migrations/` не менялись.

## Отклонения и сбои (проверено ответами сервера)

1. 000018: два вызова вернули `Invalid or expired requestState` (сбой соединения MCP, не SQL). После каждого проверено, что запись в `pgmigrations` отсутствует; после переподключения MCP применено без изменений.
2. 000027: `42501 must be able to SET ROLE "impuls_expiry_executor"` — `postgres` в Supabase не суперпользователь и не может сделать `ALTER FUNCTION … OWNER TO`. Транзакция откатилась (проверено: ролей и колонки `automatic_expiry` нет, максимум 000026).
3. Адаптация для 000027 и 000028 (только в применённом SQL, не в файлах репозитория): перед `ALTER … OWNER` добавлено `GRANT impuls_expiry_executor TO CURRENT_USER WITH SET TRUE`, после `REVOKE … FROM CURRENT_USER`. Проверка после: владелец функции — `impuls_expiry_executor`; членство `postgres` — только `admin_option=true, set_option=false` (выдано при создании роли); `CREATE` на схему у исполнителя нет.
