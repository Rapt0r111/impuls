# F08/F07: последние события симуляции

Основание: IMPLEMENTATION_PLAN.md §§ 7–8, 10–12, F08/F07 и продолжение сводки ADR-0014. Схема 000001–000022, существующие точные admin.notifications, off-by-default SYNTHETIC_NOTIFICATION_STATUS_ENABLED и private no-store GET /api/v1/admin/notifications сохраняются. Архитектура и зависимости не меняются.

Ответ дополняется обязательным recentEvents: максимум 20 записей из тех же исходных pending synthetic событий выбранной разрешённой области. Порядок created_at DESC, id DESC; время creation в UTC, отображение МСК. Поля: kind (десять известных нейтральных типов либо unsupported), createdAt, семь существующих status, nullable одна из пяти фиксированных errorCode. Идентификаторы события/получателя/источника, тексты и токены не передаются. Счётчики охватывают все события, выборка — только последние 20; это не полный список, не пагинация и не история попыток.

Область определяется сохранённой задачей/заявкой, не текущим членством получателя. Сводка и строки читаются одним statement snapshot с текущими полномочиями. Запись в outbox/receipts и бизнес-операции отсутствуют; новые гранты и миграции не нужны.

UI: встроенное закрытое details «Последние события (N)», flat semantic ordered list с типом, текстовым статусом/причиной и временем создания. Существующие refresh/loading/empty/503 retention и очистка при 401/403/404 применяются к целому ответу. Новые шрифты/цвета/анимации/зависимости не нужны. API и UI должны выпускаться совместно: поле обязательное.

Проверки: строгий контракт, запрет секретных полей/неизвестных статусов, лимит 20; PostgreSQL runtime роль — область/порядок/тай-брейк/неизменность; browser — раскрытие клавиатурой, 320/360/390/1280, увеличенный текст, reduced motion и прежние отрицательные состояния. Реальные Telegram/Bot API, полный журнал попыток, hosting, P-01…P-06 и приёмка F08/F07/R1 остаются открытыми.
