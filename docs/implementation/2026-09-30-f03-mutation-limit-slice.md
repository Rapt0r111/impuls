# F03: общий лимит изменяющих HTTP-запросов

Дата: 30.09.2026. Контракт до реализации по IMPLEMENTATION_PLAN.md §§ 4, 11–12.

- Схема: миграция 000011, одна строка `task_mutation_limits` на серверный actor UUID с FK на users (ON DELETE CASCADE), счётчиком и концом окна. RLS и гранты только серверной роли; Data API не получает доступ. Сессии, IP, токены, тела и ключи запросов не сохраняются.
- Начальное техническое значение: 30 попыток за фиксированное окно 60 секунд от первой попытки. Это не согласование P-04 и не измеренный оптимум; до пилота требуется нагрузочная проверка. Общая корзина для create, assign, start, submit, return, accept. Нельзя сбросить лимит сменой сессии, объекта, операции или Idempotency-Key.
- HTTP: после Origin, активной сессии и CSRF, до проверки объекта/ключа/тела и вызова бизнес-операции. Авторизованные ошибочные запросы и идемпотентные повторы расходуют попытку. GET, вход и выход сюда не входят; вход имеет свой существующий лимит. Отказ — 429 RATE_LIMITED с целым Retry-After (1–60 секунд), request ID и private/no-store. Отказ БД — 503 без бизнес-операции. Исчерпание не скрывает отзыв допуска или отсутствие сессии.
- Домен: отдельная короткая транзакция на один pg client, создание/блокировка строки и расчёт окна по clock_timestamp после получения блокировки. Счётчик насыщается на 31; отказ не продлевает окно. Списание попытки фиксируется до бизнес-транзакции, её rollback не возвращает попытку. Операции задач повторно проверяют права/сессию как раньше. Прямые внутренние доменные вызовы не являются HTTP и не ограничиваются этой защитой.
- UI: в трёх существующих формах текст 429 с Retry-After, сохранение данных и того же ключа/тела; повтор вручную. Отказ повтора не доказывает результат предшествующего запроса с потерянным ответом, поэтому намерение остаётся замороженным до подтверждения. Новый экран, таймер, автоматический повтор и зависимости не нужны.
- Проверки: PostgreSQL под impuls_app (31-я попытка, независимость акторов, несколько pools, истёкшее окно, блокировка через границу окна, насыщение, ACL, rollback); реальные HTTP (все маршруты, одинаковая корзина двух сессий, отсутствие бизнес-записей при 429, replay после истечения, auth/CSRF раньше лимита, GET/logout); Playwright (429 и потеря ответа→429→успешный повтор с тем же телом/ключом для отчёта, проверки и управления).

Срез локальный и синтетический. Внешний выпуск, Telegram Android/iOS, PostgreSQL 17 CI, восстановление и P-01…P-06 проверяются отдельно; F03/F04/R1 целиком не завершены.
