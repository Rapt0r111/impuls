# F07: публикация новой версии условий синтетической косметики

Основание: IMPLEMENTATION_PLAN.md §§ 4–7, 10–12, F02/F06/F07; ADR-0016. До P-решений остаются только синтетические условия, off-by-default флаги и существующие позиции. Это локальное продолжение каталога, не приёмка R1.

## Контракт до реализации

- POST /api/v1/admin/rewards/:id/versions публикует немедленную новую версию существующей synthetic/cosmetic identity. Требует active session/subject, точные admin.catalog и отдельное admin.catalog.publish в одной области, SYNTHETIC_ADMIN_CATALOG_ENABLED и новый SYNTHETIC_CATALOG_PUBLICATION_ENABLED (оба false по умолчанию). Read-only полномочие не получает запись. Полномочия не выдаются миграцией.
- Строгие path/body/headers: reward UUID, scope UUID, expectedVersion, title 1–120, conditions 1–2000, price 1–1000000, enabled boolean, reservationSeconds null либо целое 1–2592000, reason 1–2000 и Idempotency-Key UUID. Нет клиентского effectiveFrom, kind/mode, квоты или идентичности новой позиции. Origin/content-type/body size проверяются до БД; CSRF — после чтения сессии и до мутации; используется существующий общий PostgreSQL limiter мутаций по актору.
- Только append новой версии, исторические версии и снимки заявок неизменяемы. Операция запрещена при будущих условиях: их замена/отмена требует отдельного scheduling контракта. expectedVersion относится к последней сохранённой версии; UI предлагает публикацию только для текущей версии без scheduled. Нестандартная немонотонная конфигурация отклоняется, не переписывается.
- Транзакция: user → permission → session → idempotency → advisory identity → все quota rows по стабильному id. Последние версии/права/сроки перечитываются после ожидания блокировок. Новые quota inserts сериализуются прежним advisory guard. Резервирование уже держит quota до проверки latest terms; публикация ждёт все quota, поэтому завершившийся старый резерв сохраняет прежние условия, ожидающий резерв получает conflict после публикации. Балансы/квоты/заявки не меняются публикацией.
- Серверное effectiveFrom устанавливается после блокировок, version=max+1. Новые условия и append-only catalog_publications (actor, request ID, reason, previous/new version IDs, timestamp) фиксируются вместе с idempotent response. Нет outbox события или Telegram-получателей для изменения каталога: такой transport/policy ещё не задан. Ошибка откатывает всю операцию; replay проверяет текущие права/flag прежде сохранённого ответа, новое тело с тем же ключом конфликтует.
- Центральный admin.audit reader включает catalog.publish с точным synthetic scope, пагинацией native timestamp/id и отдельным строгим catalog evidence: предыдущий номер и новый immutable snapshot. Не добавляется сырой diff или данные получателя. Audit GET защищён своим прежним flag/permission независимо от publication flag. Для старых audit response catalog=null (schema default null для совместимости), старые записи не реконструируются.
- GET admin catalog добавляет canPublish для выбранной области (оба флага и два точных права); это только affordance, серверное полномочие проверяется при POST. Новый insert-only runtime grant/RLS не даёт UPDATE/DELETE на условия или журнал; worker/Data API/Public не получают доступ.
- UI расширяет существующую flat catalog row одной inline формой. Исходный номер/условия, обязательная причина, явное подтверждение немедленного изменения для будущих заявок. Цена/условия/срок старых заявок не меняются. Одна открытая форма, dirty navigation guard, Telegram Back, keyboard/focus, 320/360/390/1280, enlarged text/reduced motion. Unknown/network/503 сохраняет неизменяемое intent с прежним ключом для ручного replay; 409 требует закрыть форму и обновить каталог перед новым намерением, 429 — ручной повтор; 401/403 теряет сессию, 404 очищает protected catalog caches. Никаких автоматических новых ключей.
- Миграция 000024 и API/UI выпускаются вместе. Зависимости и архитектура сохраняются; локальные функции не объявляются production-ready. Создание identity, квоты, scheduling, supervisor/Bot API, внешний выпуск, physical devices и P-01…P-06 остаются открытыми.

## Проверки

Disposable PostgreSQL с 000001–000024: права/область/сроки/отзыв/flags, immutable grants, idempotent replay/change body, expectedVersion, scheduled/unconfigured, two publishers, публикация против блокированного reserve и истекшее право после ожидания, rollback audit failure, старые заявки/балансы/квоты неизменны. HTTP Origin/CSRF/strict body/413/405/no-store и real browser-to-DB. Контрактные негативные тесты. UI loading/empty/denial/success/unknown/conflict/429/late response, dirty/Back и мобильные снимки. Локальный restore rehearsal должен охватывать все миграции после добавления 000024.
