# Ежедневная копия Production и восстановление (P-06)

Ответственный — владелец (P-06, 10.10.2026). Цели: RPO 24 часа, RTO 1 день. Решение и его ограничения — [ADR-0034](../adr/0034-daily-backup-github-actions.md).

## Включение (один раз)

1. На своём компьютере создать ключ: `age-keygen -o impuls-backup.key`. Файл с закрытым ключом хранить вне репозитория и вне GitHub (менеджер паролей и вторая копия офлайн). Строка `Public key: age1…` — открытый ключ.
2. В GitHub → Settings → Secrets and variables → Actions добавить:
   - `BACKUP_AGE_RECIPIENT` — открытый ключ `age1…`;
   - `BACKUP_DATABASE_URL` — строка Supabase «Session pooler» (Connect → Session pooler, порт 5432) с паролем БД и `?sslmode=require` в конце. Прямая строка `db.<ref>.supabase.co` из GitHub не подключится: она IPv6, а GitHub Actions — только IPv4.
3. Actions → backup → Run workflow. Прогон зелёный, в артефакте два файла: `impuls-<время>.dump.age` и `impuls-<время>.check.json`.

После этого workflow запускается сам каждый день в 03:30 МСК.

## Что проверяет каждый прогон

`scripts/verify-backup.mjs` восстанавливает копию в пустой PostgreSQL 17.6 и проверяет:

- история миграций совпадает с началом списка `db/migrations` (Production может отставать, но не расходиться);
- для каждого участника баланс (`lifetime_xp`, `available_points`, `reserved_points`) равен сумме журнала начислений — это критерий остановки пилота P-06;
- число строк в каждой таблице (в отчёте `check.json`, без самих данных).

Красный прогон с ошибкой «did not pass the restore check» — копия сохранена, но есть расхождение. Это повод остановить пилот по P-06 и разобраться, а не перезапускать прогон. Красный прогон без артефакта — копия не сделана (секрет, сеть, Supabase приостановлен); исправить и запустить вручную в тот же день, иначе RPO нарушен.

## Восстановление

1. Скачать артефакт нужного дня (Actions → backup → прогон → Artifacts) и распаковать.
2. Расшифровать: `age -d -i impuls-backup.key -o impuls.dump impuls-<время>.dump.age`.
3. Проверить копию локально (нужен PostgreSQL 17 и клиент 17):
   `PG_BIN=<каталог bin PostgreSQL 17> TEST_DATABASE_URL=postgres://<user>@127.0.0.1:<port>/<db> node scripts/verify-backup.mjs --archive impuls.dump`
4. Восстановить в целевую БД (новый Supabase-проект или Production после аварии):
   - создать роли, которых нет: `impuls_app` (LOGIN, с паролем из окружения Vercel), `impuls_worker`, `impuls_expiry_worker`, `impuls_expiry_executor` — как в миграциях 000003, 000021, 000027; роли кластерные и в копию не входят;
   - `pg_restore --single-transaction --exit-on-error --no-owner --dbname "<строка подключения>" impuls.dump`;
   - сравнить счётчики строк с `check.json` того же дня;
   - задать новый `DATABASE_URL` в Vercel (если проект новый), пересобрать и войти через Telegram.
5. Записать в `docs/verification/` дату, какая копия, сколько заняло восстановление (RTO) и что проверено.

## Хранение

- Артефакты хранятся 14 дней, затем GitHub удаляет их сам. Срок утверждает владелец (§ 8).
- Удалённые по P-02 данные пропадают из копий не позже чем через 14 дней после удаления.
- Для копии вне GitHub владелец может раз в неделю скачивать последний артефакт в своё хранилище; это не автоматизировано.

## Открыто

- Учебное восстановление в отдельный Supabase-проект — не проводилось.
- Отдельная роль только для чтения вместо пароля `postgres` в секрете GitHub.
- Срок хранения копий (§ 8) и допустимость GitHub для хранения зашифрованной копии реальных данных (P-02).
