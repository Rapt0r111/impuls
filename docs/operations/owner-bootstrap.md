# Начальная выдача прав владельцу (P-01)

Владелец продукта — единственный администратор и командир на старте (P-01, [реестр решений](../implementation/2026-10-09-owner-decisions.md)). Приложение намеренно не делегирует права `admin.access`, `admin.access.manage` и `admin.members.manage` (ADR-0023, ADR-0026), поэтому первую выдачу выполняет оператор БД скриптом [`scripts/bootstrap-owner.mjs`](../../scripts/bootstrap-owner.mjs).

## Что делает скрипт

Одна транзакция под ролью миграций (`MIGRATION_DATABASE_URL`, прямое подключение; не роль `impuls_app`):

1. Находит пользователя по Telegram ID или создаёт активного с указанным именем. Неактивного существующего пользователя не трогает и завершается ошибкой.
2. Находит область по `--scope-id`, либо по паре «вид + имя», либо создаёт её. Несколько областей с одним именем — ошибка.
3. Выдаёт все 21 действие из `permissionActions` (`task.*`, `reward.*`, `admin.*`, `ledger.correct`), которых в этой области ещё нет в действующем виде. Повторный запуск ничего не добавляет. Отозванные и истёкшие права выдаются заново.
4. Без `--apply` откатывает транзакцию и печатает план (сухой прогон — режим по умолчанию).

Выдача идёт с `granted_by` = сам владелец и причиной «Начальная выдача владельцу». Запись `access_changes` не создаётся: триггер `guard_access_change` запрещает самовыдачу, а эта выдача — единственное исключение, поэтому в журнале доступа её нет; след — строки `role_bindings`.

Что скрипт **не** делает: не добавляет членство владельца в области (допуск самого себя запрещён, ADR-0026), не выдаёт права другим людям, не меняет существующие данные, не обращается к Telegram.

## Запуск

```bash
MIGRATION_DATABASE_URL=postgres://… node scripts/bootstrap-owner.mjs --telegram-id <ID> --name "<имя>" --scope-name "<название области>" --scope-kind project
```

Затем тот же вызов с `--apply`. Параметры: `--scope-id <uuid>` вместо `--scope-name`; `--scope-kind rota|group|project` (по умолчанию `project`). Telegram ID владельца в репозиторий не записывается. Выдача отзывает открытые сессии пользователя (триггер `role_bindings_revoke_sessions`) — потребуется повторный вход.

## Проверено

- `vitest run tests/integration/owner-bootstrap.test.ts` на PostgreSQL 18.6 (`127.0.0.1:45432`): 7 тестов — создание и самовыдача всех действий, идемпотентность, сухой прогон без записей, перевыдача только отозванного права, область по id и неизвестный id, отказ для неактивного пользователя, отказ на неверный ввод. Тест сверяет список скрипта с `permissionActions`: расхождение ломает тест. Перед реализацией тест падал на отсутствии модуля.
- Ручной запуск CLI на той же БД: сухой прогон, `--apply`, повторный `--apply` (`granted: []`), ошибка на нечисловой ID.

## Не проверено

- Запуск самого скрипта против Supabase/Production: не выполнялся (строки подключения владельца схемы у исполнителя нет). Выдача выполнена 09.10.2026 SQL-эквивалентом через Supabase MCP после применения 000032–000035; см. [запись выпуска](../verification/2026-10-09-production-migrations-32-35-owner-grant.md). Решение P-02 о разрешённом контуре не подтверждено.
- Вход владельцем после выдачи в браузере/Telegram.
